Part 1 — System architecture

The Test Development Kit (TDK) drives a browser-based Couchbase Lite JavaScript test server, which performs all CBL operations. Python pytest orchestrates setup, assertions, and remote admin APIs.

┌─────────────────────┐ WebSocket ┌──────────────────────────┐ │ Python TDK client │ ◄────────────────► │ JS test server (Vite) │ │ (cbltest / pytest) │ localhost:5173 │ @couchbase/lite-js │ └──────────┬──────────┘ └────────────┬─────────────┘ │ │ │ HTTP admin / REST │ CBL Replicator ▼ ▼ ┌─────────────────────┐ ┌──────────────────────────┐ │ Couchbase Server │ │ Remote (one of): │ │ (datasets, N1QL) │ │ • Sync Gateway :4984 │ │ localhost:8091 │ │ • Edge Server ws://:59840 │ └─────────────────────┘ └──────────────────────────┘

Why JavaScript is different from other platforms

  • Other platforms (C, .NET, JVM) expose an HTTP test server in-process.
  • JS runs in a browser — it cannot open a listener. The “server” is a WebSocket client that connects back to Python.
  • Browser CBL cannot use HTTPS/WSS to Edge Server in this setup — local ES must be HTTP + ws://.

Part 2 — End-to-end data flows
Flow A — Default: JS CBL ↔ Sync Gateway
  1. pytest loads config.docker-js.json → connects to JS server on :5173 via WebSocket router.
  2. CouchbaseCloud.configure_dataset() resets CBS bucket + configures SG database (e.g. travel) from dataset/sg/{name}-sg.json.
  3. POST /reset to JS server → browser opens local CBL DB, loads dataset from repo (or GitHub in prod builds).
  4. POST /startReplicator → JS CBL replicator targets http://localhost:4984/{db} (SG REST).
  5. pytest polls POST /getReplicatorStatus until activity = STOPPED.
  6. Assertions compare local CBL vs remote (SG REST or CBS N1QL).
This path is the baseline. 78 runnable tests pass here.
Flow B — JS CBL ↔ Edge Server (--cbl-remote=es)
  1. Same pytest + JS server setup as Flow A.
  2. install_es_remote() replaces cblpytest.sync_gateways[0] with EsRemote adapter.
  3. configure_dataset is monkeypatched → creates ES database via HTTP admin, bulk-loads same {name}-sg.json docs (no CBS bucket recreate).
  4. Replicator URL becomes ws://localhost:59840/{db} (must be ws://, not wss://).
  5. Query-consistency tests POST CBL SQL++ to ES: POST /{db}.{scope}.{collection}/_query instead of CBS N1QL.
  6. Tests that need SG channels, roles, _purge, or sync functions are skipped via ES_SKIP_FILES.
# EsRemote duck-types Sync Gateway for tests:
replication_url(db)  → ws://host:59840/db
get_document(...)    → Edge Server REST
update_documents(...)→ Edge Server bulk API
add_user / add_role  → no-op (ES has no SG ACL model)
Flow C — JWT smoke: Edge Server ← Sync Gateway (not CBL→ES remote swap)

These tests do not use --cbl-remote=es. They configure ES to pull from SG using JWT auth while JS CBL may push directly to ES over ws://.

  1. Real SyncGateway object remains (for local_jwt, SG admin).
  2. ES config gets replications pointing at live SG URL; pinned_cert dropped when SG is HTTP.
  3. ES databases declare collections (create: true alone only gives _default._default).
  4. 7 tests in test_edge_server_cbl.py + edge_server/ — all pass locally.
Flow D — Single test request lifecycle (WebSocket)
pytest WebSocket router Browser (tdk.html) │ │ │ │── POST /reset (JSON) ───────►│── ws message ts_command ────►│ │ │ │── CBL Database.open / load dataset │◄── ts_id response ───────────│◄── ws response ──────────────│ │ │ │ │── POST /startReplicator ────►│─────────────────────────────►│ │ │ │── new Replicator({ url: ws://ES/... }) │── POST /getReplicatorStatus ─►│─────────────────────────────►│ (poll every 1s) │◄── activity: IDLE|STOPPED ───│◄─────────────────────────────│

Tests treat STOPPED on a one-shot (continuous: false) replicator as “replication job finished.”

Part 5 — The 8 interop failures (detailed, one section each)
All 8 tests pass against Sync Gateway with the same JS client and same test code. Failures are specific to the JS CBL → Edge Server path.
Interop test_push_document_ids_filter

File: tests/dev_e2e/test_replication_filter.py

Purpose: Verify CBL pushes only documents whose IDs appear in the replicator’s documentIDs filter.

Steps

  1. Load travel dataset on remote and in local CBL.
  2. First push — filter airlines: airline_10, airline_20, airline_1000; routes: route_10, route_20. Wait STOPPED. Expect 4 doc events (1000 absent locally).
  3. Local edits: add airline_1000, update airline_10, delete route_10.
  4. Second push — same filter. Wait STOPPED. Expect events for airline_1000, airline_10, route_10.

Failure: CblTimeoutError: Timeout waiting for replicator status at step 4.

Interop test_pull_document_ids_filter

File: tests/dev_e2e/test_replication_filter.py

Purpose: Same as push, but pull direction — only listed airport/landmark IDs sync down.

  1. First pull with document ID filters → wait STOPPED → verify 4 docs.
  2. Modify remote (add/update/delete docs) → second pull → wait STOPPED → verify filtered changes.

Failure pattern: Same as push — typically hangs on second one-shot run (IDLE, never STOPPED).

Interop test_custom_pull_filter

File: tests/dev_e2e/test_replication_filter.py

Purpose: Pull with CBL-side filter deletedDocumentsOnly — only tombstones pass the filter.

  1. Pull with filter → expect zero docs (nothing deleted yet).
  2. Delete docs on remote → pull again → expect only deleted IDs replicate locally.

Note: test_custom_push_filter (push + filter) passes on ES because filtering runs locally before push.

Failure: Pull with filter — replicator stays IDLE, test waits for STOPPED.

Part 6 — Root cause analysis
Problem 1 — One-shot replicator stays IDLE (7 tests)

Symptom

pytest calls wait_for(ReplicatorActivityLevel.STOPPED, timeout=30s). Against ES, activity remains IDLE after replication work completes. Document listener shows expected doc events.

What this is NOT

  • Not missing dataset / collections (first push passes; docs arrive)
  • Not SG or CBS misconfiguration (SG path identical and passes)
  • Not pytest timeout misconfiguration (SG reaches STOPPED well under 30s)

Likely cause (interop)

For one-shot replication, CBL clients expect the session to end in STOPPED. Sync Gateway elicits that from lite-js; Edge Server does not (or lite-js does not interpret ES completion the same way).

Ownership: Edge Server replication session lifecycle vs SG-compatible behavior — and/or lite-js handling of ES BLIP/WebSocket completion. SG is confirmed not at fault (same client passes).

Replicator activity states (reference)

StateMeaningTest expectation
CONNECTINGOpening connectionTransient
IDLEConnected; may have finished syncES gets stuck here
STOPPEDOne-shot job finishedTests wait for this
Problem 2 — _attachments assertion (1 test)

Sync Gateway REST returns revision metadata including _attachments with stub entries for blobs. Edge Server returns the document body with blob properties inline; it does not mirror SG’s attachment map.

Classification: API shape difference + test written for SG. Blob replication itself works on ES.

Fix options: Skip step 7 for ES runs; extend EsRemote.get_document() to synthesize SG-shaped stubs; or document ES blob REST model for TDK.

Part 7 — Expected skips (not Edge Server bugs)

Many tests are skipped on ES by design. Extra Docker or config will not turn these into passes.

Skipped because Edge Server lacks Sync Gateway features
  • Channels / roles / sync functions — fest (7), auto-purge (13), channel filters (2)
  • _purge API — checkpoint reset tests (2)
  • ES 1.2 ACL is collection read/write only, not SG channel ACL
Skipped because JavaScript CBL cannot run them (any remote)
  • Multipeer (2) — no P2P API in lite-js
  • Encrypted properties (1) — C-only EncryptedValue
  • SGW upgrade (13) — requires native CBL ≥ 4.0
  • XDCR (2) — multi-SG topology + CBL ≥ 4.0
  • Blob compact (1) — JS excluded (CBSE-14861)

Environment note — dataset loading

JS TDK loads datasets via HTTP fetch. In Vite dev, datasets must be served locally (/local-dataset/); GitHub raw URLs fail in browser with TypeError: Failed to fetch. This was fixed for investigation and is unrelated to ES replication protocol.

Part 9 — Recommendations for Edge Server team
  1. Investigate one-shot replication session completion
    Compare BLIP/WebSocket session teardown with Sync Gateway for: document-ID filters (2nd run), pull filters, conflict resolver pulls. Goal: client observes STOPPED after work completes, matching SG behavior.
  2. Document expected client-visible activity transitions
    Clarify whether IDLE is terminal for non-continuous replications on ES, or if STOPPED should follow.
  3. Blob document REST shape
    Document how clients should verify blob presence on ES (no _attachments). If SG parity is desired, specify equivalent metadata.
  4. Regression tests
    Consider ES-native tests for: filtered push/pull second run, conflict resolver pull, blob push — with explicit session state assertions.
What already works: Basic push/pull (10/12), all 34 SQL++ query consistency tests, custom push filter, JWT ES←SG replication, direct JS push over ws://.
